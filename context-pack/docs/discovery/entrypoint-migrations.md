## What it does

On every `backend` container start, [backend/entrypoint.sh](../../backend/entrypoint.sh) waits for Postgres, then runs `python manage.py makemigrations --noinput` for `api`, `backlog`, and `practicehub` in sequence, followed by `migrate --noinput`, `collectstatic`, and the seed commands, before starting Gunicorn. Because `./backend:/app` is a bind mount ([docker-compose.yml](../../docker-compose.yml)), any migration file `makemigrations` generates inside the container is written back onto the host — it becomes a real file in the working tree, not a container-only artifact.

This means the set of migration files on disk is not fixed by what a developer wrote and reviewed; it is regenerated by whatever the current model state happens to be every time the container restarts, on every machine, in every environment that runs this entrypoint.

## Data

**Reads:** the current state of `models.py` in `api`, `backlog`, `practicehub`, and the migration history table Django keeps in Postgres.
**Writes:** new `*.py` migration files under each app's `migrations/` directory (on the host, via the bind mount), and schema changes to the `amplify` database.
**External calls:** none beyond Postgres.

### Undocumented rules

**R1 — Rules 1 and 2 above contradict each other in practice**
- Behaviour: migrations are meant to be committed (R2) but are regenerated at runtime on every start (R1). Whichever version happens to exist in the working tree at the moment someone runs `git add`/`git commit` is what gets committed — not necessarily what the original author of a model change reviewed.
- Trigger: any container restart following any uncommitted model change, by anyone, on any machine.
- Consequence if dropped/ignored: migration files can silently differ between two developers' machines, or between a developer's machine and CI/production, if a model change is present but `makemigrations` hasn't been run and committed deliberately by a human.
- Characterisation test: none exists today.

**Concrete evidence this has already happened:** [backend/api/migrations/0006_alter_integrationhubproject_emoji.py](../../backend/api/migrations/0006_alter_integrationhubproject_emoji.py) and [0007_alter_integrationhubproject_emoji.py](../../backend/api/migrations/0007_alter_integrationhubproject_emoji.py) are two separate migrations, generated 13 minutes apart on the same day (2026-06-12, per their generated headers), both altering the exact same field (`IntegrationHubProject.emoji`) — the first sets `default='📁'`, the second reverts it to `default=''`. This is the signature of `makemigrations` firing across two container restarts during one edit session, rather than a single reviewed migration.

## Traps for a new maintainer

- Editing a model and not restarting the backend container will make local testing appear to work (SQLite-style autoreload intuition does not apply) while the migration for that change does not yet exist anywhere.
- Two developers changing the same model concurrently will each get their own machine-generated migration file when they next restart, with a high chance of conflicting migration numbers/dependencies on merge.
- `azure-pipelines.yml` does not run `makemigrations` — CI does not regenerate migrations, so a migration that only exists because a local container generated it, and was never committed, will not exist in CI or production at all, and `migrate` there will apply a different (older) schema than what the running local environment has.
